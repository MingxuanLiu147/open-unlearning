# MMUnlearner Sidecar 后续实验记录（2026-03-24）

## 1. 本轮实验目标

- 验证现有 checkpoint `saves/mm_unlearn/test_ga_f10` 是否可在 GPU 上完成最小评估闭环。
- 验证当前环境下可复现的多模态 sidecar 启动方式，避免 `python src/mm_*.py` 带来的 CUDA 丢失问题。
- 在确认评估链路后，继续推进最小训练复现实验。

## 2. 环境与启动方式结论

本轮首先定位了一个环境相关问题：

- 直接执行 `python src/mm_eval.py ...` 或 `python src/mm_train.py ...` 时，`torch.cuda.is_available()` 会变为 `False`。
- 设置 `CUDA_VISIBLE_DEVICES=<id>` 也会让当前进程中的 CUDA 变为不可用。
- 使用 `python -u ...` 同样会导致 `torch.cuda.is_available()` 变为 `False`。
- 将 Python 输出重定向到文件（例如 `> log 2>&1`）时，CUDA 也会失效。

当前环境下可工作的启动方式是：

- 不设置 `CUDA_VISIBLE_DEVICES`
- 不使用 `python -u`
- 不做 stdout/stderr 重定向
- 采用 `python -c 'import torch; ...; sys.path.insert(0, "..."); import runner; runner.main()'` 的交互式启动方式

为此，本目录新增了两个实验 runner：

- `run_mm_eval_existing_checkpoint.py`
- `run_mm_train_minimal.py`

这两个 runner 的目的不是替代 repo 正式入口，而是在当前沙箱内提供一个可复现、可保住 CUDA 的实验入口。

## 4. 关键技术结论

1. 旧总结文档中“最小训练尚未跑通”的结论已经部分过时。
   当前 repo 中至少已存在一个可加载的 `Qwen3-VL-4B` merged checkpoint：`saves/mm_unlearn/test_ga_f10`。

2. 当前真正的主要阻塞不再只是 OOM。
   更现实的阻塞是“入口启动方式会让 CUDA 消失”，这会导致看似能运行，实际退化到 CPU。

3. `mm_eval.py` 原始实现存在设备放置问题。
   已在源码中补上“若 CUDA 可用则显式 `model.to(device)`”的逻辑。

4. 评估 merged checkpoint 时不能再次启用 LoRA 注入。
   因此实验 runner 中默认对现有 checkpoint 使用 `lora.enabled = false`。

5. 当前最小训练链路已经实测可跑通。
   至少在本轮配置下，`Qwen3-VL-4B + LoRA + batch_size=1 + grad_accum=8 + epoch=1` 可以在当前环境完成 1 轮训练并成功保存模型。

## 8. 新增技术结论

1. `MMKLMin` 与 `MMNPO` 在 `Qwen3-VL-4B` 上可以通过极小样本 smoke 配置完整跑通训练与评估，但较大 smoke 配置仍容易 OOM。
2. `SFRon` mask 生成链路已跑通，但要稳定运行需要：
   - 使用本地 snapshot 路径
   - 关闭 LoRA
   - 极小样本
   - 在 `compute_fisher()` 之间显式释放梯度缓存
3. 当前环境下，`PYTORCH_ALLOC_CONF=expandable_segments:True` 也会破坏当前可用的 CUDA-safe 启动方式，不能作为通用补救手段。
4. `MMUnlearner` 代码层之前确实存在 `forget_alpha` 死参数问题，本轮已修复。
5. `MMUnlearner` 在默认 LoRA 训练设置下仍存在方法语义风险：
   - mask 基于 base weights
   - trainable params 却主要是 LoRA adapter
   - 因此当前实现距离“真正达到论文方法效果”仍有明显差距

## 9. 新增：旧/新 GA checkpoint 的 targeted MLLMU 对照评估

为避免在当前机器上直接跑完整 `retain_shared` 长评估耗时过长，本轮补做了一个可比的 targeted 对照：

- classification：
  - split: `forget + retain_shared + retain_celebrity + test`
  - `max_records=10`
- generation：
  - split: `forget + test`
  - `max_records=5`
  - `generation_max_new_tokens=64`

注意：

- `max_records` 是按原始 parquet 记录数截断，不是按展开后的 QA 数截断。
- 因此 classification 结果里每个 split 的 `total=100`，generation 结果里每个 split 的 `total=20`，都是展开后的题目数。
- 这组结果用于快速比较 forget/retain/test 方向，不替代完整 benchmark。

- 相反，这个最小 checkpoint 更像是整体回答能力更强一些，但遗忘更弱一些。

- 但新 checkpoint 在 `test` generation 上明显更强，说明它的通用回答能力更好。

### 本轮新增结论

1. `MMGradAscent` 最小复现实验的产物已经不只是“能训完”，而且可以在 targeted `classification + generation` 上与旧 checkpoint 做直接对照。
2. 在当前 targeted 对照里，新最小 GA checkpoint 的趋势很一致：
   - forget 指标更高
   - retain/test 指标也更高
3. 这意味着当前最小训练配置更像是在“保留更多整体能力”，而不是“做出更强遗忘”。
4. 因此，后续若要继续追 `MMGradAscent` 的多模态 unlearning 效果，优先级应放在：
   - 增强 forget 强度，而不是只验证能否收敛
   - 补完整 benchmark，而不是继续重复当前这组最小训练参数
5. 本轮 observed 的推理速度差异没有纳入方法结论。
   - 旧 checkpoint 的 targeted classification 运行时，机器上还有并发文本实验占用多张 GPU。
   - 新 checkpoint 的 targeted classification 运行时，后台负载已显著下降。
   - 因此本轮只记录效果指标，不把吞吐差异解释为 checkpoint 本身性质。
